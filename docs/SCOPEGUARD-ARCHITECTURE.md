# ScopeGuard architecture and upgrade boundaries

The existing application uses vanilla JavaScript and CSS, a Python local HTTP server, and Flask on Vercel. Hosted persistence is PostgreSQL (Neon); local accounts use SQLite. Cookie sessions and password-encrypted ML-DSA-65 keys are shared. The existing protocol signs terms, delivery, decisions and cancellation using purpose-separated contexts. Solidity contracts and the offline CLI remain unchanged. Hosted files use private Cloudflare R2 with conservative quota reservations; metadata remains in Postgres.

ScopeGuard adds a separate versioned project workflow inside this same app, account system and database. Existing PQE-v1 bundles are preserved. ScopeGuard hashes canonical JSON and signs a domain-separated hash envelope using the existing ML-DSA-65 implementation. Proposals are immutable snapshots. An active version changes only after both stored signatures verify. Pending amendments block delivery and financial actions. Amendments after delivery or financial outcomes are intentionally refused in this prototype.

Milestones reserve **simulated test ETH** from the existing spendable test-wallet funds atomically with journal updates. These are database-backed conditional reservations, not Solidity locks, INR payments or mainnet transactions. Legacy escrow deposits remain separate and unaffected. This avoids claiming offline promises reserve money when they do not. Disputes freeze release; only mutual identical signed resolutions can refund, release or split remaining reserved test funds.

ScopeGuard analysis is a deterministic, bounded demo service. It does not call an external model, infer visual quality, execute uploaded code, or decide payments. A provider interface separates generation from the workflow. Every generated term is a proposal. PDF extraction is optional via pypdf; missing/unsupported extraction produces human-review results. ZIP contents are inspected in memory with expansion/entry bounds and are never executed or extracted to disk. Keyword matches are evidence of text presence only, never proof of feature behavior.

New tables store projects, immutable versions, signatures, deliveries, reports, disputes, evidence, payment journal and chained audit events. Requirements and milestone definitions live in the canonical version snapshot; status and evidence are derived from append-only records. No unsigned client payment or verification status is trusted. Private API access requires project membership, with only aggregate opt-in reputation exposure omitted: passports are self-only to reduce disclosure.

Limitations: server-custodied signing keys, no malware scanner or sandbox execution, no autonomous arbitration, no real-money payments, no Sybil-resistant identity proof. Reputation is labelled observed test activity, distinct-counterparty counts are shown, demo projects are excluded, and the product does not call these metrics verified identities or fraud-proof reputation.
